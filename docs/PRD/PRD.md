# MeLog PRD

[HTML] https://melog-prd.gihae.chatgpt.site

## 1. 제품 개요

### 1.1 제품명

**MeLog**

### 1.2 한 줄 설명

사용자가 일상에서 경험한 행동, 감정, 생각을 기록하면 AI가 이를 구조화하고, 장기간의 기록에서 반복되는 패턴과 가설을 발견할 수 있도록 돕는 자기 관찰 서비스.

### 1.3 제품 목적

MeLog는 사용자의 성격이나 적성을 단정하는 서비스가 아니다.

사용자가 실제 경험을 기록하고 그 기록을 근거로 자신에 대한 가설을 세운 뒤, 작은 실험을 통해 가설을 다시 검증할 수 있도록 지원하는 것을 목적으로 한다.

서비스의 기본적인 사고 흐름은 다음과 같다.

```text
관찰
↓
기록
↓
근거 축적
↓
패턴 발견
↓
가설 생성
↓
작은 실험
↓
새로운 기록
↓
가설 재판단
```

AI는 사용자를 판단하는 주체가 아니라 이 과정을 돕는 **분석 보조자** 역할을 한다.

---

# 2. 문제 정의

## 2.1 현재 문제

자신이 어떤 일을 좋아하는지, 어떤 상황에서 몰입하는지 판단하려면 실제 경험을 계속 관찰할 필요가 있다.

하지만 일상적인 경험을 매번 직접 정리하는 것은 번거롭다.

또한 하나의 경험만으로 다음과 같이 판단하기 쉽다.

```text
오늘 디버깅이 재미있었다.
→ 나는 개발이 적성인가?
```

하지만 하나의 사례만으로 이러한 결론을 내리기는 어렵다.

필요한 것은 여러 경험을 기록하고 반복되는 행동과 감정을 확인하는 과정이다.

---

## 2.2 해결하고자 하는 문제

MeLog는 다음 문제를 해결한다.

* 경험을 체계적으로 기록하기 어려움
* 행동과 감정을 객관적으로 정리하기 어려움
* 하나의 경험만으로 성급한 결론을 내릴 가능성
* 여러 기록에서 반복되는 패턴을 직접 찾기 어려움
* 자신의 가설을 실제 경험으로 검증하기 어려움

---

# 3. 핵심 제품 원칙

## 3.1 판단보다 관찰

AI는 사용자를 특정 성향이나 유형으로 판정하지 않는다.

잘못된 예:

```text
당신은 백엔드 개발에 적성이 있습니다.
```

권장되는 형태:

```text
최근 문제의 원인을 추적하는 활동에서
지속적으로 높은 몰입과 만족을 기록하고 있습니다.

문제 해결 과정 자체에 흥미를 느낄 가능성이 있습니다.
추가적인 경험을 통해 확인할 필요가 있습니다.
```

---

## 3.2 가설은 항상 잠정적이어야 함

AI 분석 결과는 사실과 가설을 구분한다.

예:

```text
관찰
오류 발생 후 로그를 계속 확인함

감정
답답함 → 해결 후 만족감

행동
로그 확인
원인 추적 지속

가설
문제의 원인을 추적하는 활동에 흥미가 있을 가능성

근거
현재 한 개의 사례만 존재함
```

---

## 3.3 기록이 판단의 근거가 되어야 함

사용자의 자기 이해는 AI의 추측이 아니라 사용자가 직접 기록한 경험을 기반으로 해야 한다.

---

## 3.4 작은 실험을 통해 가설을 검증

가설이 만들어졌다고 끝나는 것이 아니다.

다음 경험을 의도적으로 만들어 가설을 검증할 수 있어야 한다.

예:

```text
가설

문제의 원인을 추적하는 일을 좋아한다.

↓

작은 실험

Spring 프로젝트의 오류 하나를 직접 분석해본다.

↓

새로운 기록

오류를 찾는 동안 계속 집중했고
해결 후 만족감이 컸다.

↓

근거 추가

기존 가설을 지지하는 사례 추가
```

# 4. 목표 사용자

초기 주요 사용자는 다음과 같다.

### 진로나 적성을 고민하는 사람

예:

* 대학생
* 취업 준비생
* 직무 전환을 고민하는 사람

### 자신의 행동 패턴을 알고 싶은 사람

예:

* 무엇을 좋아하는지 명확하지 않은 사람
* 어떤 상황에서 몰입하는지 알고 싶은 사람
* 자신의 경험을 체계적으로 돌아보고 싶은 사람

초기 MVP에서는 특정 사용자 집단을 세밀하게 구분하지 않는다.

# 6. MVP 범위

MVP에서는 다음 네 가지 기능만 구현한다.

## 6.1 기록 작성

사용자는 자연어로 경험을 작성할 수 있다.

필수 정보:

* 기록 내용
* 작성 시간

사용자는 정해진 양식을 작성할 필요가 없다.

예:

```text
오늘 Spring 공부를 했는데
개념을 읽는 것은 조금 지루했지만
직접 오류가 난 부분을 찾는 것은 재미있었다.
```

---

# 6.2 AI 분석

기록 저장 시 AI가 내용을 분석한다.

분석 결과에는 다음 항목이 포함된다.

### 관찰

기록에서 객관적으로 확인 가능한 상황.

### 감정

사용자가 표현한 감정.

### 행동

사용자가 실제로 수행한 행동.

### 가설

행동과 감정을 기반으로 만든 잠정적인 해석.

### 근거 수준

현재 기록만으로 해당 가설을 어느 정도 판단할 수 있는지 표현한다.

### 다음 작은 실험

가설을 추가로 확인하기 위해 시도해볼 수 있는 간단한 행동.

---

# 6.3 기록 저장

다음 정보를 저장한다.

```text
원본 기록
AI 분석 결과
작성 날짜
```

MVP에서는 원본 기록과 AI 분석 결과를 함께 저장한다.

# 6.4 과거 기록 조회

사용자는 이전 기록 목록을 볼 수 있다.

목록에서는 다음 정도의 정보만 제공한다.

```text

기록 내용 일부
주요 감정
```

기록을 선택하면 상세 내용을 볼 수 있다.

상세 화면에서는 다음을 보여준다.

```text

관찰

감정

행동

가설

근거 수준

다음 작은 실험
```

# 10.2 감정 구조화

예:

```text
재미
만족

지루함

```

---

# 10.3 반복 패턴 분석

여러 기록을 분석한다.

예:

```text
최근 기록 12개 중

문제 해결과 원인 추적 활동 5개에서
높은 만족감이 반복적으로 나타남.
```

---

# 10.4 가설 관리

개별 기록에서 생성된 가설을 별도의 대상으로 관리한다.

예:

```text
가설

문제의 원인을 추적하는 활동을 좋아하는 것 같다.

관련 기록

#13 Spring 오류 해결
#18 Linux 서버 오류 분석
#27 API 오류 추적

지지 근거
3건

반대 근거
1건
```

---

# 10.5 작은 실험 관리

AI가 제안한 작은 실험을 실제 수행 여부와 연결한다.

```text
가설

문제 추적을 좋아한다.

↓

실험

처음 보는 Spring 오류를 직접 해결해본다.

↓

실험 기록

재미있었음

↓

가설 근거 추가
```

---

# 10.6 가설 변화 추적

가설은 시간이 지남에 따라 변화할 수 있다.

```text
초기

문제 해결 활동을 좋아하는 것 같다.

↓

기록 추가

문제 해결보다는
원인을 분석하는 과정에서 만족도가 높음.

↓

수정된 가설

문제를 직접 해결하는 것보다
원인을 분석하고 추적하는 과정에
흥미를 느끼는 것일 수 있다.
```

# 11. 핵심 데이터 개념

장기적으로 다음 네 개의 핵심 개념을 사용한다.

```text
Entry
사용자가 작성한 경험 기록

Analysis
하나의 Entry에 대한 AI 분석

Hypothesis
여러 기록을 기반으로 형성되는 사용자에 대한 잠정적 가설

Experiment
Hypothesis를 확인하기 위해 수행하는 작은 실험
```

MVP에서는 우선 다음 두 개를 중심으로 구현한다.

```text
Entry

Analysis
```

`Hypothesis`와 `Experiment`는 향후 기능으로 확장한다.

# 12. AI 분석 원칙

AI는 다음 규칙을 따른다.

### 사실과 해석을 분리한다.

사용자가 실제로 한 행동과 AI의 가설을 구분한다.

### 사용자가 말하지 않은 사실을 만들어내지 않는다.

기록에서 확인할 수 없는 감정이나 의도를 단정하지 않는다.

### 하나의 기록으로 사용자의 적성을 판단하지 않는다.

### 가설에는 불확실성이 포함되어야 한다.

예:

```text
~일 가능성이 있다.

현재 기록만으로 판단하기 어렵다.

추가적인 사례가 필요하다.
```

### 행동 가능한 작은 실험을 제안한다.

너무 큰 목표를 제안하지 않는다.

잘못된 예:

```text
백엔드 개발자로 취업해보세요.
```

권장 예:

```text
30분 정도 새로운 오류 하나를 직접 추적해보고
그 과정에서 느낀 감정을 기록해보세요.
```

# 13. 비기능 요구사항

## 데이터 보존

사용자가 작성한 원본 기록은 AI 분석 결과와 별도로 보존한다.

AI 분석 방식이 변경되더라도 원본 기록을 다시 분석할 수 있어야 한다.

## AI 오류 대응

AI 분석에 실패하더라도 사용자가 작성한 기록 자체가 유실되어서는 안 된다.

## 확장성

향후 다음 관계를 추가할 수 있도록 데이터 구조를 지나치게 고정하지 않는다.

```text
Entry
↓
Analysis

Entry 여러 개
↓
Hypothesis

Hypothesis
↓
Experiment

Experiment
↓
Entry
```

# 14. MVP 성공 기준

MVP의 성공은 기능 개수보다 다음 질문으로 판단한다.

### 사용자가 부담 없이 경험을 기록할 수 있는가?

### AI 분석이 사용자의 경험을 이해하는 데 도움이 되는가?

### AI가 단정하지 않고 관찰과 가설을 구분하는가?

### 과거 기록을 다시 확인하고 싶다는 가치가 있는가?

### 기록이 반복될수록 자신에 대해 새로운 것을 발견할 가능성이 있는가?

이 질문에 긍정적인 답을 얻는 것이 1차 목표다.

# 16. 장기 제품 방향

MeLog의 최종 목표는 많은 기능을 가진 일기 서비스가 아니다.

사용자가 자신의 경험을 근거로 자신에 대해 계속 새로운 가설을 만들 수 있는 시스템을 만드는 것이다.

```text
경험

↓

기록

↓

AI 구조화

↓

근거 축적

↓

패턴 발견

↓

가설

↓

작은 실험

↓

새로운 경험

↓

가설 수정
```

이 반복 구조 자체가 MeLog의 핵심 제품 가치다.
